# VP Workbench

基于 Tauri v2 的桌面视频处理工作台，当前围绕"配置先行"的单一工作流构建：

1. `home`：启动探测、能力缓存与运行时概览
2. `input`：批量导入素材
3. `decode`：解码方案与硬件设备
4. `preprocess`：解码后帧级滤镜链（含 Anime 清理）
5. `enhance`：补帧 / 超分
6. `postprocess`：增强后帧级滤镜链（含 Anime 清理）
7. `encode`：编码器与输出配置
8. `render`：批处理队列与任务日志

## 仓库结构

- `backend/`：Python CLI 与流式处理链路
- `contracts/`：JSON Schema 2020-12 中立边界与唯一 IPC manifest
- `frontend/`：Vue 3 + TypeScript + Pinia + Vue Router
- `frontend/src-tauri/`：Tauri v2 桌面外壳、权限与运行时桥接
- `docs/`：开发文档（见下方导航）
- `scripts/`：契约生成、freshness、依赖边界和零冗余门禁

## 当前桌面命令面

桌面端只保留下面这些 Tauri commands，并与权限清单一一对应：

- `pick_inputs`
- `pick_output_directory`
- `check_environment`
- `load_workbench_preset`
- `save_workbench_preset`
- `inspect_video`
- `check_resume_state`
- `start_task`
- `control_task`（统一 pause / resume / cancel）
- `open_output_location`

`contracts/ipc-manifest.json` 是命令名、参数、返回值和事件的唯一清单。任务控制只通过
`control_task` 接收 `pause | resume | cancel`，不存在独立的暂停、恢复或取消命令。

后端 CLI 保留五个外部入口：

- `python -m app check`
- `python -m app info --input <video>`
- `python -m app process --input <video> ...`
- `python -m app inspect-output --input <video> ...`（由 Tauri 主机在启动 `process` 前做续传预检）
- `python -m app benchmark ...`（开发 / CI 性能回归门禁）

另有隐藏的 `stage-worker` 子命令，只由 Python 流水线为隔离算法 stage 拉起，不属于桌面壳公共命令面。

## 生成物与忽略规则

- 根 `.gitignore` 只处理仓库级缓存、样例媒体和工作区产物。
- `backend/.gitignore` 负责 Python 缓存、运行日志、输出目录和本地模型权重。
- `frontend/.gitignore` 负责 `node_modules`、`dist`、`src-tauri/target` 以及 Tauri 自动生成权限文件。
- `contracts/boundary.schema.json`、`backend/app/generated/contracts.py`、`frontend/src/types/generated/contracts.ts`、前端 IPC/事件适配器和 Rust manifest/事件适配器都是受 Git 跟踪的生成物；运行 `python scripts/generate_contracts.py --check` 可验证逐字节 freshness。
- `frontend/src-tauri/permissions/autogenerated/` 是构建时生成目录，默认忽略，不手工维护。
- `frontend/src-tauri/gen/schemas/*.json` 是当前仍受 Git 跟踪的生成文件，修改命令面或权限后需要一并同步。

## 持久化与桌面安全边界

当前持久化版本为环境缓存 `14`、工作台预设 `2`、分段清单 `3`。损坏或版本不匹配的数据会被
改名隔离并重建，不会迁移、解析或回退读取；预设加载失败会通过全局 `IssueBanner` 告知用户。

Tauri capability 只授权本地 `main` 窗口，不授权任何远程 origin。CSP 将脚本限制为自身资源，
连接限制为 Tauri IPC，并禁止 `object` 与 `frame`；安全约束由 Rust 单测和桌面 E2E 共同验证。

## 运行时资源解析

桌面外壳会按以下顺序解析运行时资源：

1. 显式环境变量覆盖，例如 `VP_FFMPEG_PATH`、`VP_FFPROBE_PATH`、`VP_RIFE_MODEL_DIR`、`VP_RUNTIME_ROOT`
2. canonical `$RUNTIME_ROOT`（bundle/debug 均为 `resources/runtime/`）中的打包资源
3. 开发环境下的工作区源码布局
4. 仅 Python 可继续从系统 `PATH` 解析；FFmpeg / FFprobe 在 release 中没有系统路径兜底

### Python 环境配置

Release 构建默认不打包 Python 运行时。应用启动时按以下优先级查找 Python：

1. `VP_PYTHON_EXECUTABLE` 环境变量（绝对路径）
2. 打包目录中的 bundled Python（`resources/runtime/python/python.exe`）
3. 系统 `PATH` 中的 `python.exe`（Windows）或 `python3`（Linux/macOS）

若系统 PATH 中已存在兼容的 Python（3.12+），无需额外配置即可运行。
若需指定特定 Python 环境，请设置环境变量：

```powershell
$env:VP_PYTHON_EXECUTABLE = "D:\Python312\python.exe"
```

### TensorRT 加速（可选）

ONNX 引擎默认走 CUDA EP。若想启用 TensorRT EP 拿到额外性能，需要：

1. 安装 `onnxruntime-gpu` 1.20+（自带 TRT provider DLL）
2. 下载并解压 NVIDIA TensorRT 10.x（与 CUDA 版本匹配，例如 CUDA 13 对应 TRT 10.14）
3. 把解压根目录设到 `VP_TENSORRT_DIR`，例如 `D:\TensorRT-10.14.1.48`

桌面外壳优先使用 `VP_TENSORRT_DIR`，也会识别 `$RUNTIME_ROOT/tensorrt/`。解析结果通过
`build_env_map` 投影给 Python 子进程，后端 `register_native_dll_paths` 会在创建 ONNX session
前自动把 `<dir>/bin` 注册到 DLL 搜索路径，无需手动改系统 PATH。没有可用 TensorRT 目录时引擎
自动降级到 CUDA EP。
